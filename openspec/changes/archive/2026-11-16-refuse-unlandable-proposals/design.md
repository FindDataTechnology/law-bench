# 设计：预检放在提交面，尺子借用确认侧

## D1 为什么拒在提交口，而不是在确认口警告

确认口警告（「这条会改写既有单位」）保留信息、不改行为，看起来更保守。但它把成本留在
原位：舰队每天照样提交重复键，负责人照样一条条看、一条条驳。实测 8 条重复键提案就是这么
消耗掉的。**提交口拒绝才是让这条规则执行一次、而不是每天执行一次。**

代价是「用提案通道更新既有单位」这条路暂时被堵。它今天其实也不存在：8 条重复键提案
全部被负责人以「如需补充定义请更新既有单位而非新建」驳回——即**域负责人已经就这条做过
裁决**，预检只是把这条裁决写成机器可执行的那一半。等机器面有了 update 通道，拒绝文案里
就该指向它；在那之前指向控制台的更新入口。

## D2 尺子必须是确认侧那把

预检如果自带一套「键存在吗」的判断，就会与确认行为分叉：预检放行的、确认时失败（假绿），
或者预检拒掉的、确认其实会成功（假红，且比假绿更糟——它让舰队停止提交正当内容）。

所以只用两个**既有**读判据，都是确认侧写的：

- 实体/关系分道：`_lane_for_kind`（读域锚定模板的 `entity_types` / `relationship_kinds`）
- 活单位集合：`authoring.authoring_live_key_kinds`（`namespace = 域 key` 且
  `tags->>'deleted' IS NULL` 的 `{key: kind}`）
- 单条读取：`authoring.authoring_get_unit`（与 kernel 写路径同一个 `store.get_knowledge_unit`）

`authoring_live_key_kinds` 存在的理由本身就记录过两次事故（1000 行上限把「存在」读成
「缺失」），此处复用它，不再写一条自己的 `SELECT`——本项目对 `knowledge_units` 的 SQL
只允许在 kernel/store 里出现（`proposals.py` 的模块注释明说「no INSERT INTO knowledge_units」，
本变更把这条纪律扩到「也不自己 SELECT 它」）。

## D3 两类理由各自点名，不合并成一个「不合格」

`key_already_live` 与 `endpoints_missing` 的处置方向不同（前者「别重复提，要改走更新」，
后者「先把端点提上来再提关系」）。合并成一句「提案不合法」会让提交方修错方向——这正是
`fleet-submitter-contract` 第一条 requirement 已经确立的原则：告诉调用方该修什么，
而不是「forbidden」。

同键异 kind 也走 `key_already_live`，但 detail 里写明既有 kind：同一键在两种 kind 下
各存一条，是键归名逻辑一直在防的那种「两条单位」问题，不该由预检放行。

## D4 顺序：去重在前，预检在后

`submit()` 现有三步：① 同键同依据（跨提交方）去重 → ② 同来源同键待确认去重 →
③ 同键同依据已驳回 ⇒ 「需新证据」。预检插在 ③ 之后、INSERT 之前。

理由：① ② 命中时根本不写行，重放必须是 `created=false`（这是舰队「新增 vs 幂等命中」报数
的基石）。若预检排在前面，「第一份提案刚被确认」之后的合法重放会变成 409，把幂等语义打穿。

## D5 只在机器面返回 409，库层仍抛异常

库层（`proposals.submit`）抛 `ProposalTargetExists(ValueError)`，带 `reason` /
`external_key` / `hint` 三个机器可读字段；HTTP 面映射成 **409**。
不直接把状态码写进库层：应用内的其它提交方（`extract:` 流水线、控制台）需要的是异常类型，
不是 HTTP 语义。

## D6 端点「已在箱里」也算成立（实跑逼出来的）

第一版只认活单位，`tests/test_ontology_extraction.py::test_same_batch_entity_closes_the_endpoint`
当场转红（`submitted` 3→2）：进程内抽取流水线在**同一批**里提交实体提案与闭合它的关系，
提交关系那一刻端点还是一行 pending，不是单位。这说明「端点不闭合」的判据少一档——
**同一批里正在闭合**与「压根没有这个端点」是两件事，把它们并成一档会把正当流水线拒掉，
而假红比假绿更糟（它教人停止提交正当内容）。

所以判据改成「活单位 ∪ 本域待确认提案键」。代价是评审若先确认关系、后确认实体，内核
仍会失败——这与改造前完全一样，不是新增风险；收益是批量抽取这条主路不被误伤。
