# 提案落不下去时，拒在提交口

## Why

`legal` 域自 2026-11-08 起共 95 条舰队提案，其中 **41 条被驳回**，理由聚成三类
（生产库 `domain_proposals.decision_note` 实测）：

| 理由 | 条数 | 现状 |
| --- | --- | --- |
| 键已在库（同一概念/机关早前已确认为本体单位） | 8 | 提交时无人检查，占了负责人的确认位 |
| 文种名/角色名或不含可复用原理，不作为概念入库 | 7 | 语义判断，只能人判（不在本变更内） |
| 关系端点不闭合：一端尚未入库 | 4 | 提交时无人检查，确认时必失败 |

前两类之外的这两类（12 条）是**确定性**的：它们与提交内容无关，只看「目标域此刻有没有
东西」和「两个端点是不是都活着」。把它们留给人判，等于让人反复执行一条机器就能执行的
规则，而人眼是这套流程里最稀缺的资源。

更要紧的是第一类的**风险方向**：确认一步走的是单位 upsert
（`src/bench/authoring.py` `_create_unit` → kernel `write`），所以确认一条「键已存在」的
提案不是「再加一条」，而是**改写既有单位的正文**。今天没有出事，只因为负责人每次都用手
把它们驳回去了——这条防线是人，不是代码。提交方在提交那一刻读不到这件事，也无从知道
自己提的是「新建」还是「覆盖」。

## What Changes

- **提交前预检**（`src/bench/proposals.py`）：在写入提案行之前，用**确认时同一把尺子**
  检查两类确定性落不下去的提交，当场拒（不入库、不占确认位）：
  1. 实体类提案的 `external_key` 在目标域已是**活单位** ⇒ 理由 `key_already_live`，
     点名既有单位的 id 与 kind（含「同键异 kind」——那会造出同一键的两条单位）；
  2. 关系类提案的任一端点不在该域活单位集合里 ⇒ 理由 `endpoints_missing`，点名缺哪个。
- **机器可判别**：HTTP **409** + 稳定的理由词；`hint` 写明两条正当路径（改既有单位走更新、
  端点在别的域/未入库则先补端点）。客户端已把 409 归为不可重试的 `conflict`，
  提案员的提示词已有「拒绝按原文原因记录、同批不重提」的纪律。
- **顺序纪律**：预检必须排在幂等去重**之后**。同一主张的重放仍返回既有提案与
  `created=false`；预检只回答「这条此刻落不落得下去」，不改幂等语义。

不动的东西：语义类驳回（文种名/角色名/不复用）仍归人；确认路径不变；`extract:` /
`agent:` / `user:` 三类来源的校验不变。

## Impact

- Affected spec: `fleet-submitter-contract`（新增一条 requirement）
- Affected code: `src/bench/proposals.py`、`src/web/routes/distribution.py`、测试
- 生产影响面：只影响**新提交**。既有 95 条提案一行不动（它们已是既成事实，正/误判都
  留着当史料）。判据方向是「以后不再产生这两类」。
