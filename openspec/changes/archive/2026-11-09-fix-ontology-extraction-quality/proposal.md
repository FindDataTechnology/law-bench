## Why

抽取管道已验证可用（逐字证据闸、只进提案层、幂等、上限都成立），但**产出不可用**。2026-11-09 生产小样 20 块的 9 条候选暴露四类问题：

```
[law]     宪法 / 中华人民共和国宪法 / 中华人民共和国宪法修正案   ← 同一实体三个键
[law]     中华人民共和国                                    ← 错：这是国家不是法
[clause]  第十二条 / 第三十二条                              ← 歧义：几乎每部法都有
[clause]  序　言 → 键 "序-言"                                ← 全角空格折叠；且序言不是条款
[cites_law] 第十二条 → 宪法                                  ← 端点全靠上面的歧义键
```

按现状扩量只会堆出一个满是歧义键的提案箱，人工复核成本高于手写——**这不是调提示词能解决的**：提示词只能缓解「类型判错」，解决不了「条款键必须带父法」。

## What Changes

- **条款键带父法**：条款类实体的外部键改为 `<法规键>#<条款号>`，并把 `law_id`/`chunk_no` 记进属性以便溯源。裸条款号不再被接受。
- **只认真正的条款**：条款号必须匹配 `第<数字>条`（含中文数字），`序言`/`目录`/`第X章`/`第X节` 一律不算条款。
- **实体别名归一**：新增 `canonical_name` 与 `aliases`，同一实体在批内归一到一个键；归一用**显式规则**（去「中华人民共和国」前缀、去书名号等），不用模糊相似度。
- **类型后置校验**：`law` 类候选的名字必须能在被引块的 `title` 里找到（归一后子串匹配），否则拒——这条专门挡「中华人民共和国被标成 law」。
- **抽取报告给可用率**：`usable_rate = submitted / produced` 与按 kind 的分布一起报告；低于阈值时批次标注「低产」，提示别扩量。

## Capabilities

### New Capabilities

- `ontology-key-scheme`: 本体实体的**标识与归一口径**——什么样的键是可用的、同名实体如何归一、条款如何带父法、以及抽取产出的可用率如何判定。这是「候选能不能用」的契约，比抽取本身更基础。

### Modified Capabilities

- `ontology-extraction`: 候选生成后新增「键与归一」与「类型后置校验」两道关，并新增可用率报告；其余（逐字证据、只进提案层、词表、幂等、上限）不变。

## Impact

- 代码：`src/bench/extraction.py`（键生成、条款解析、别名归一、类型校验、报告字段）；`src/bench/ontology_import.py` 的 `is_smoke`/键口径需与新规则对齐（导入同样要产出可用键）。
- 数据：仅 `knowledge_units.attrs` / `tags` 增加 `canonical_name`、`aliases`、`law_key`、`clause_no`（JSONB，无 schema 变更）。
- 兼容：已有 16 条 pending 候选是旧口径产出的，键不合规；本变更不迁移它们——它们本就是待驳的低质样本。
- 风险：归一规则写错会把**不同**法规合成一个（比拆开更危险），因此归一必须是显式白名单式规则 + 单测逐条钉住；不做模糊合并。
