## Context

The repo has two unrelated assets: (1) per-contract-type 法律法规 surveys answered by Doubao and DeepSeek (`output/law_info/{deepseek,doubao}/<type>.md`, 41 types, registry in `output/law_info/contract_types.json`), with an existing pure extractor `src/eval/legal_refs.extract_references` that pulls `《...》`-wrapped law names and categorizes them; and (2) a standalone `src/docs/` module (`create_docx`, `docx_to_pdf`, `create_pdf`, and a `{{slot_name}}` slot model with `find_slots`/`fill_slots`) added by the archived `add-docx-pdf-generation-slots` change. Nothing connects them: there is no tool that, for a contract class, extracts its 法律法规 and emits a fillable contract PDF/DOCX with slots and slot instructions, and none of it is on the web (`src/web/`, FastAPI, already exposes `/law-info` and `/law-references` from a DB-backed `law_info` table). Constraints: the tool must run both locally (macOS) and in the Linux/k3s container (which already has the `libreoffice` PDF layer); no new Python dependencies may be added.

## Goals / Non-Goals

**Goals:**
- A `src/contracts/` package + CLI (`python -m src.contracts`) that, per contract class, extracts the 法律法规 from the Doubao+DeepSeek answers, builds a slot-based contract template with a per-slot instruction manifest, and generates DOCX/PDF via `src/docs/`.
- A reusable Python API (`list_contract_types`, `get_template`, `get_slot_instructions`, `extract_laws_for_type`, `generate_contract`) shared by the CLI and the web layer.
- Web routes (`/contracts`, `/contracts/{type}`, `/contracts/{type}/download/{format}`) showing the template, slots+instructions, 法律法规, and DOCX/PDF download.

**Non-Goals:**
- Modifying `document-generation` (consumed as-is) or the existing `law-info-web`/`/law-references` pages (linked, not modified).
- Auto-drafting contracts via the CrewAI pipeline; slot validation against an external schema; in-browser slot-filling/form submission; mail-merge.
- Bespoke per-type legal prose for all 41 contracts (v1 uses a standard skeleton; richer authoring is a follow-up).

## Decisions

### D1: Reuse the `document-generation` slot model; slot instructions live in `src/contracts/`
**Choice**: Slots remain `{{slot_name}}` tokens handled by `src/docs/`. A *slot instruction* (`name`, `label`, `description`, `example`, `required`) is metadata about a slot, owned by `src/contracts/slots.py` - not a new concept in `src/docs/`.
**Rationale**: Keeps `document-generation` (and its spec) stable; instructions are a contracts-layer concern. `find_slots` already gives the slot names in a template body, so instruction coverage is checked against that.
**Alternatives**: Extend `src/docs/` with an instruction model - rejected, it would change a stable capability and couple generic doc tooling to contract semantics.

### D2: Templates are a parameterized skeleton, stored as committed data
**Choice**: A standard contract skeleton (title; parties; recitals; subject matter; rights & obligations; term; price/payment; breach & liability; dispute resolution; governing law; signatures) with `{{slot}}` placeholders and a per-type slot set. Template bodies + slot instructions are generated by `scripts/seed_contract_templates.py` into a committed registry `src/contracts/data/contracts.json` (`[{key, zh, body, slot_instructions:[{name,label,description,example,required}]}]`); `templates.py` loads it.
**Rationale**: Authoring 41 bespoke contracts is out of scope for v1; a skeleton with type-specific slots/instructions is achievable, consistent, and fillable. A JSON registry separates data from code and mirrors the existing `seed_*.py` pattern.
**Alternatives**: 41 hand-authored Markdown files - high effort, deferred. Hard-coded Python dict - less reviewable than JSON data.

### D3: Legal extraction reuses `extract_references`, file-backed (no DB) so the CLI is standalone
**Choice**: `extract_laws_for_type(contract_type)` reads `output/law_info/{deepseek,doubao}/<type>.md`, builds `{contract_type, source, content}` items, and calls `src.eval.legal_refs.extract_references`, returning the laws whose `contract_types` include the type as `[{name, category, category_zh, sources}]`. The law-info source directory is overridable (default `output/law_info/`).
**Rationale**: `extract_references` is the existing, tested extraction logic; reusing it avoids divergence. Reading the committed markdown keeps the CLI standalone (no DB), so the tool works in any environment that has the repo.
**Alternatives**: Use `src.eval.law_info.all_law_info(db)` (DB-backed) - would couple the CLI to a database; rejected for the tool. The web layer calls the same file-backed function for consistency.

### D4: Generation facade over `src/docs/`
**Choice**: `generate_contract(contract_type, *, format="pdf", out_dir=None)` resolves the template + instructions + laws, then: always builds the DOCX via `src.docs.create_docx(body, <out_dir>/<type>.docx, title=zh_name)` with `slots=None` (so every `{{slot}}` stays a highlighted, fillable placeholder); for `pdf`/`both`, converts via `src.docs.docx_to_pdf`. It returns `{docx_path, pdf_path, slots, instructions, laws}` (unset formats -> `None`), where `slots` comes from `src.docs.find_slots` on the generated DOCX. Default `out_dir` is `output/contracts`.
**Rationale**: `slots=None` guarantees fillable templates (the user fills slots later, guided by the instructions); `find_slots` confirms the generated file's slots match the manifest.
**Alternatives**: Pre-fill some slots at generation - rejected; the deliverable is a fillable template, not a filled contract.

### D5: CLI `python -m src.contracts`
**Choice**: `__main__.py` -> `cli.py` using `argparse`: positional `contract_type` (required unless `--all`), `--format {pdf,docx,both}` (default `pdf`), `--all` (iterate every type in `contract_types.json`), `--out DIR` (default `output/contracts`). On `NotFoundError`, print an error naming the type to stderr and exit 1; on success, print the generated path(s) to stdout.
**Rationale**: Simple, scriptable, matches the user's "a tool to extract the information and generate the pdf" ask. `--all` enables batch generation.
**Alternatives**: A Click/Typer app - rejected (no new dependency; argparse suffices).

### D6: Web routes share the `src.contracts` API
**Choice**: `src/web/routes/contracts.py` (APIRouter, `tags=["contracts"]`): `GET /contracts` (list via `list_contract_types`), `GET /contracts/{type}` (detail: `get_template` + `get_slot_instructions` + `extract_laws_for_type`), `GET /contracts/{type}/download/{format}` (calls `generate_contract(..., format=...)` then `FileResponse`). Registered in `app.py` via the existing lazy-include block. Templates `contracts_list.html` and `contract_detail.html` extend `base.html`; the detail page renders the body with `src/web/markdown_render.render_markdown` and groups 法律法规 by `CATEGORY_ORDER`/`CATEGORY_ZH`.
**Rationale**: The web layer is a thin view over the same API the CLI uses - no duplicated generation/extraction logic. Follows the existing `law_info`/`pages` router pattern.
**Alternatives**: A JSON-only API - rejected; the user asked to add it "to the web" (HTML pages with download links).

### D7: Download is generate-on-demand
**Choice**: `/contracts/{type}/download/{format}` generates the file to `output/contracts/<type>.<ext>` on each request and streams it via `FileResponse`.
**Rationale**: Simplest correct behavior; avoids stale-cache issues. PDF cold-start (~1-3s, inherited from LibreOffice) is acceptable for low/medium volume.
**Alternatives**: Pre-generate all 41 at deploy and serve static files - follow-up if latency or volume demands it.

## Risks / Trade-offs

- **[Generic v1 template bodies]** -> v1 uses a skeleton, not bespoke per-type legal prose. Acceptable for fillable templates; richer authoring is a follow-up (D2).
- **[Extraction depends on `《》`-wrapped law names]** -> inherited from `extract_references`; laws not wrapped in `《》` are missed. Documented; out of scope to change here.
- **[PDF backend availability]** -> `docx_to_pdf` raises `ConverterNotAvailableError` if `soffice` is absent (inherited). The container has the `libreoffice` layer; local dev needs `brew install --cask libreoffice`. Download returns a clear error if unavailable.
- **[File-backed vs DB-backed law_info]** -> `src/contracts` reads `output/law_info/` directly while `law-info-web` reads the DB. Slight inconsistency, but keeps the CLI standalone (D3). The committed markdown is the source of truth for both.
- **[Generate-on-demand latency]** -> ~1-3s per PDF download (D7). Acceptable for low volume; caching/pre-generation is a follow-up.

## Migration Plan

1. Add the `src/contracts/` package (`__init__.py`, `templates.py`, `slots.py`, `legal.py`, `generator.py`, `cli.py`, `__main__.py`).
2. Author `scripts/seed_contract_templates.py` and run it to produce/commit `src/contracts/data/contracts.json` (41 templates + slot instructions).
3. Add `src/web/routes/contracts.py` + `contracts_list.html` / `contract_detail.html`; wire the router into `src/web/app.py`; add a `/contracts` nav link in `base.html`.
4. No database migration (file-backed) and no new dependencies.
5. **Rollback**: remove `src/contracts/`, `src/web/routes/contracts.py`, the two templates, and revert the `app.py`/`base.html` edits. No existing route is affected.
