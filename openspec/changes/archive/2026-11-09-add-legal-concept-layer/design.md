## Context

见 proposal.md 的取证。两条事实决定做法：

- `guide_cases`（293 条）在 **`law_db`（100.64.0.5）**，字段齐全：`gist` 280 条、`statutes` 280 条、`title`、`case_no`。它**不在** Qdrant 的 `law_chunks_v2` 里——那条集合只有法规条文分块。
- 抽取的 `sample_chunks` 目前只认 qdrant。它要的东西其实很少：`chunk_id`、`text`、`title`（父法/来源）、`law_id`。与向量无关。

## Goals / Non-Goals

**Goals**

- 让 `concept` 有地方存在（模板词表），并让抽取能从**裁判要点**这种语料面产出概念。
- 起始概念集小而立得住：20 条左右、每条可溯源，用来验证「概念→法条」这条路通了。
- 不动主线域，除非人决定升版。

**Non-Goals**

- 不做概念体系（上下位、同义、部门法归属）的完整建模——先能挂住、能引用。
- 不做全量 293 条案例的抽取（先起始集，扩量另议）。
- 不从 `keyword` 批量建实体（603/715 是一次性标签，是案件类别，不是概念）。

## Decisions

**D1 概念用 `defines` 关系挂法条，方向是 概念 → 法条。**
语义是「该概念由该条确立/界定」。反过来（法条 defines 概念）会让法条成为关系的承载者，而法条本身已经是实体；以概念为主语更符合复核者的问题（「这个概念依据在哪」）。
- 备选：用 `cites_law`（条款→法规已有）——但 `cites_law` 的语义是「条款引用法规」，套到概念上会污染那条关系的含义。

**D2 概念键 = 归一名，不带父法。**
复用 `keys.slug(canonical_name(...))`。理由与条款相反：条款的地址必须带父法（第十二条到处都有），概念恰恰**跨法**存在（违约责任在合同法与民法典里是同一个概念）。

**D3 语料接入走「按需读表」而不是灌 Qdrant。**
抽取只需要文本。为 293 条案例去跑一遍嵌入管线（RustFS 导出 → 嵌入 → 灌集合）成本远高于收益，且会把裁判要点混进「法规检索」的语义空间——检索“法条”却返回裁判要点，是另一种混淆。
- 代价：需要一个 `law_db` 只读连接（第四个凭据）。**这是本变更唯一需要人点头的基础设施项**；替代方案是由法规数据线把裁判要点灌成独立集合，但那要跨仓排期。
- 实现上给 `sample_chunks` 增加 `source_kind='text-table'` 分支：`uri` = 表名，`ingest_rule` 描述列映射（text/title/id/statutes）。

**D4 起始集靠人工挑，不靠批量规则。**
从 gist 里挑「抽象到能跨案复用」的说法（居间合同、和解协议、连带清偿责任、举证责任⋯），逐条带 `source_case_no` 与 `statutes`。数量少但每条都经得起看。
- 备选：把高频主题词自动转实体——实测前几名是民事/刑事/行政，会立刻污染本体。

**D5 模板升版与域升版分开做。**
先发 v2 模板（纯增量），`legal` 域**仍钉 v1**；域升版是单独的、可回退的动作，由人决定何时做。这样模板改错不会立刻影响主线域。

## Risks / Trade-offs

- **概念边界没有客观标准**：「合同」与「居间合同」谁更基础？起始集只求「能用」，不追完备；后续必然要重排层级。
- **第四个凭据**：`law_db` 只读 DSN 进 law-bench 命名空间。与 `FDTEXT_DATABASE_URL` 同样的处理（独立 secret、只读角色、用完可撤）。
- **域不升版时概念无处可去**：v2 模板发出来后，`legal` 域仍只认 `clause`/`law`。这是有意的（先看模板对不对），但意味着「真填概念」要等升版决定。
- **`defines` 指向的实体可能还没建**：概念可以先立、依据后补；复核页标「待补依据」而不是拒绝创建，否则概念永远立不起来。
