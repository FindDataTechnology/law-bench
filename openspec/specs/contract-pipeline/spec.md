# contract-pipeline Specification

## Purpose
Orchestrate contract drafting end to end: fill slots with an LLM, cache fills, self-heal failures, default to the latest rubric version, and persist each run for audit and replay.

## Requirements
### Requirement: Pipeline Orchestration
The system SHALL orchestrate the contract pipeline as a LangGraph `StateGraph` (package `langgraph`) hosted inside the `pipeline_run` MCP tool, whose nodes call the existing MCP tool functions (`contract_generate`, `contract_evaluate`) plus an LLM `fill` node and a `store` node. The graph SHALL be linear with a conditional self-healing edge: `generate -> fill -> evaluate -> check`; `check` SHALL route to `store` (terminal) when `all_pass` is true OR `iteration >= max_iterations`, otherwise to `improve -> generate` (re-run with adjusted inputs). The graph state SHALL accumulate `contract_type, tags, stance, rubric, task_desc, fill_mode, temperature, iteration, gen_result, body_text, filled_text, fill_values, fill_cache_id, eval_result, eval_run_id, best, actions_taken, recommendations`. `store` SHALL persist the **best-scoring** run observed across iterations, not necessarily the last.

#### Scenario: graph runs the happy path
- **WHEN** the first iteration yields `all_pass=true`
- **THEN** the graph executes `generate -> fill -> evaluate -> check -> store` and stops, with `iteration=1`

#### Scenario: graph loops then stops at the cap
- **WHEN** no iteration yields `all_pass=true` and `max_iterations=3`
- **THEN** the graph runs `generate -> fill -> evaluate -> check -> improve` at most twice more, then stores the best-scoring run

#### Scenario: graph nodes call the MCP tool functions
- **WHEN** the `generate` and `evaluate` nodes run
- **THEN** they invoke the in-process `contract_generate` and `contract_evaluate` tool functions (not a separate service / protocol)

### Requirement: LLM Slot Fill
The `fill` node SHALL fill **every** `{{slot}}` in the assembled `body_text` (required and optional) with a concrete value, producing `filled_text` and a `fill_values` dict. Values SHALL be generated by an LLM (`DRAFTER_MODEL` via `litellm`, mirroring `src/clauses/extract.py`), grounded by `contract_type`, `scenario` (from `tags`), and each slot's `SlotInstruction` (`label` / `description` / `example`), so the filled contract is coherent and scenario-aware. `temperature` SHALL be configurable per `pipeline_run` call (default `0.0`). Unfilled slots (e.g. an LLM omission) SHALL be left as `{{slot}}` and recorded in `actions_taken`.

#### Scenario: all slots are filled
- **WHEN** the `fill` node runs on a sale contract with slots `party_a, party_b, subject, amount, ...`
- **THEN** `filled_text` contains no `{{slot}}` tokens and `fill_values` has an entry for every slot

#### Scenario: scenario-aware fill
- **WHEN** `fill` runs with `contract_type="sale"`, `scenario="农产品买卖"`
- **THEN** the `subject` value reflects the agricultural scenario (e.g. a grain / quantity), not the generic example

### Requirement: Fill Cache
The system SHALL cache LLM fill results in a `fill_cache` table so identical inputs are deterministic and amortize the LLM cost. The cache key SHALL be `hash(contract_type | scenario | sorted(slots) | model | temperature)`. The `fill` node SHALL `SELECT fill_values FROM fill_cache WHERE cache_key = ?` first; on a hit it SHALL reuse the cached values and skip the LLM call; on a miss it SHALL call the LLM and `INSERT` the result. Each `fill_cache` row SHALL record `fill_values` (JSONB), `temperature`, `model`, and `created_at`. Each `pipeline_runs` row SHALL snapshot `fill_cache_id`, `fill_temperature`, and `fill_values` so a single run is self-describing even if the cache is later evicted.

#### Scenario: cache hit reuses fill values
- **WHEN** `fill` runs with inputs identical to a prior run (same type, scenario, slots, model, temperature)
- **THEN** no LLM call is made and the cached `fill_values` are reused

#### Scenario: cache miss populates and records temperature
- **WHEN** `fill` runs with inputs not in `fill_cache`
- **THEN** the LLM is called, a `fill_cache` row is inserted with the `temperature` used, and `pipeline_runs.fill_temperature` matches it

#### Scenario: changed slot set is a cache miss
- **WHEN** the self-heal loop excludes a clause whose `{{slot}}` disappears, changing the slot set
- **THEN** the new slot set produces a different `cache_key` and the LLM is called once for it

### Requirement: Self-Healing Loop
On a failing eval (`all_pass=false` and `iteration < max_iterations`), the `improve` node SHALL diagnose the failing `criteria_results` together with the per-section resolved clauses (via `clause_list` + the assembly resolution) and emit a structured action with two parts:
- **applied (per-run, safe)**: `exclude_custom_clause_ids: list[int]` - custom clause ids to omit from the next `generate` call (forwarded as `contract_generate(custom_clause_ids=...)`), so a thin override can be dropped and the rich base can win **for this pipeline run only**. The shared `clauses` table SHALL NOT be mutated by the loop.
- **recorded (not applied)**: `recommendations: list[{clause_id, action, reason}]` - persisted on `pipeline_runs.recommendations` for a human to apply later (e.g. via `clause_review`); the loop SHALL NOT execute them.

`check` SHALL keep the best-scoring run (by `n_passed`, then `score`) as the survivor; `store` persists that best run. The loop SHALL stop early when an iteration yields `all_pass=true`.

#### Scenario: loop excludes a thin override per-run
- **WHEN** a thin custom clause overrides the rich base for a failing section
- **THEN** the next `generate` call omits that clause via `custom_clause_ids`, the rich base is restored for that run, and no `clauses` row is modified

#### Scenario: recommendations are recorded, not executed
- **WHEN** the `improve` node suggests rejecting clause X
- **THEN** `pipeline_runs.recommendations` records `{clause_id: X, action: "reject", reason: ...}` and `clause_review(X, ...)` is NOT called by the loop

#### Scenario: best run survives
- **WHEN** iteration 1 scores 4/10 and iteration 2 scores 6/10 but neither passes all criteria
- **THEN** `store` persists the iteration-2 run (6/10) with `iteration=2`, `best` noted

### Requirement: Rubric Latest-Version Default
When `rubric` is not supplied to `pipeline_run`, the system SHALL select the latest-version rubric for the contract type: the highest trailing `v<N>` among rubrics whose name matches `^contract_<type>_v(\d+)$`; if none match that pattern, the most recent `created_at` among `contract_<type>_*` rubrics; if none exist, raise a tool error. An explicit `rubric` argument SHALL override the default.

#### Scenario: latest version is selected
- **WHEN** `pipeline_run` is called with `contract_type="sale"` and no `rubric`, and both `contract_sale_v1` and `contract_sale_v2` exist
- **THEN** the run is judged against `contract_sale_v2`

#### Scenario: explicit rubric overrides
- **WHEN** `pipeline_run` is called with `contract_type="sale"`, `rubric="contract_sale_v1"`
- **THEN** the run is judged against `contract_sale_v1` regardless of newer versions

#### Scenario: no rubric for the type surfaces an error
- **WHEN** `pipeline_run` is called with a `contract_type` that has no `contract_<type>_*` rubric and no `rubric`
- **THEN** the tool returns an error and no `pipeline_runs` row is written

### Requirement: Pipeline Runs Persistence
The system SHALL persist every `pipeline_run` to a `pipeline_runs` table (idempotent `CREATE TABLE IF NOT EXISTS` via `ensure_schema`, same `law_bench` Postgres) with columns: `id` PK, `contract_type`, `tags` (JSONB), `stance`, `rubric_name`, `task_desc`, `fill_mode`, `fill_values` (JSONB), `filled_text` (TEXT), `eval_run_id` (INTEGER -> `eval_runs.id`), `score`, `max_score`, `n_passed`, `n_criteria`, `all_pass` (BOOL), `iteration` (INT), `actions_taken` (JSONB), `recommendations` (JSONB), `fill_cache_id` (INT), `fill_temperature` (FLOAT), `created_at`. `eval_run_id` SHALL reference the `eval_runs` row created by `contract_evaluate` (its `run_id`). `pipeline_list` / `pipeline_get` SHALL read this table; `pipeline_get` SHALL join `eval_run_id` to `run_get` for the per-criterion verdicts.

#### Scenario: pipeline_runs row links to the eval run
- **WHEN** a `pipeline_run` completes
- **THEN** the `pipeline_runs.eval_run_id` equals the `run_id` returned by `contract_evaluate`, and `pipeline_get` returns both the pipeline fields and the eval criteria

#### Scenario: schema is idempotent
- **WHEN** the server starts and `ensure_schema` runs
- **THEN** `pipeline_runs` and `fill_cache` are created with `CREATE TABLE IF NOT EXISTS` and existing tables are not recreated or dropped
